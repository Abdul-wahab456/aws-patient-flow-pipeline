## 1. Project summary

An end-to-end, code-first data pipeline on AWS that ingests **synthetic hospital data in FHIR format** (generated by Synthea), processes it through a **bronze → silver → gold medallion architecture**, and produces **patient-flow KPIs** (length of stay, 30-day readmissions, admissions/discharges, ED volume).

**Goals**

- Hands-on AWS data-engineering experience using **AWS CLI, Python code and CloudFormation (YAML)** (no console clicking for building resources).
- Practice with healthcare data (FHIR JSON), nested JSON flattening in PySpark, incremental loads, Iceberg `MERGE`, star-schema modeling, and orchestration.
- A clean, documented **GitHub portfolio project**.

## 3. Architecture

```
  Synthea (laptop) --> split into 10 packets --> S3 landing/   (one-time upload)

                 start-execution {"batch": N}   (by hand; upgraded in Phase 10 to an EventBridge rule on new files)
                              |
                              v
                 Step Functions  (manager, runs steps in order)
                              |
     +------------------------+------------------------+
     |                                                 |
     v                                                 v
  [1] Lambda  ---->  [2] Glue job  ---->  [3] Athena MERGE  ---->  [4] DQ checks
  copy packet        clean + flatten      upsert into gold         test gold data
     |                    |                     |
     v                    v                     v
  BRONZE              SILVER                 GOLD                  Notebook
  S3 bronze/   -->    S3 silver/     -->     S3 gold/       -->    KPI charts
  FHIR JSON           Parquet                Iceberg tables        (awswrangler)

  Top row    = AWS services doing the work
  Bottom row = where the data is stored (all folders in one S3 bucket)
```

**One run per batch (Step Functions)** - started with `aws stepfunctions start-execution --input '{"batch": N}'`:

1. `pf-ingest` Lambda copies `landing/batch_NN/` -> `bronze/patient_records/ingest_date=YYYY-MM-DD/` and writes a batch metadata file.
2. Glue job flattens FHIR bundles for that `ingest_date` -> silver Parquet tables (catalog updated).
3. Athena runs `MERGE INTO` statements (dims first, then fact) -> gold Iceberg tables.
4. Athena runs data-quality check queries; fail the execution if a check fails.

Running the same batch again is safe: every step is idempotent.

**Upgrade (Phase 10):** the run starts by itself when a batch's marker file `landing/batch_NN/_SUCCESS` appears (EventBridge rule), and the Lambda checks the file count written in the marker.

## 4. Data source: Synthea

- Download: `https://github.com/synthetichealth/synthea/releases/download/master-branch-latest/synthea-with-dependencies.jar` (save to `data_generation/`, **gitignored**).
- Generate a **small** population with limited history to control size and cost, e.g.:

  ```powershell
  java -jar synthea-with-dependencies.jar -p 300 -s 42 `
    --exporter.years_of_history 5 `
    --exporter.fhir.export true `
    Massachusetts
  ```

  (Verify flags against the Synthea README; adjust `-p` if output is too large. Target total raw size: **< 500 MB**.)

- Output (`output/fhir/`):
  - One **FHIR transaction Bundle JSON per patient** (Patient, Encounter, Condition, Observation, etc. in `entry[].resource`).
  - `hospitalInformation*.json` → Organization / Location resources.
  - `practitionerInformation*.json` → Practitioner / PractitionerRole resources.
- **References**: Synthea uses both `urn:uuid:<id>` references and conditional references like `Organization?identifier=...|<id>` / `Practitioner?identifier=...|<npi>`. **Inspect real samples first** and write a helper that resolves both formats into plain IDs.

**Simulating a daily feed**

- `data_generation/split_batches.py` splits patient bundle files into **10 batches** (the project uses only batches 1-4 for now; the rest wait in `data/landing_extra/`) → `data/landing/batch_01 … batch_10`.
- `hospitalInformation*` and `practitionerInformation*` go into **batch_01**.
- A batch = a group of patients. The **simulated arrival date** is deterministic: `ingest_date = 2026-11-01 + (batch_number - 1) days`.
- Upload the batch files once: `aws s3 sync data/landing s3://<LAKE_BUCKET>/landing/` (done in Phase 3). In Phase 10 a batch "arrives" when its marker `landing/batch_NN/_SUCCESS` (JSON `{"files": <count>}`) is written - the usual convention for "the delivery is complete".

## 6. Data model

### 6.1 Silver tables (`pf_silver`, Parquet, partitioned by `ingest_date` string `YYYY-MM-DD`)

| Table          | Columns (minimum)                                                                                                                                                                                                               |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `patient`      | patient_id, gender, birth_date, deceased_datetime, marital_status, city, state, postal_code, ingest_date                                                                                                                        |
| `encounter`    | encounter_id, patient_id, status, encounter_class (e.g. AMB/EMER/IMP —**check distinct values in data**), type_code, type_display, start_ts, end_ts, organization_id, practitioner_npi, reason_code, reason_display, ingest_date |
| `condition`    | condition_id, patient_id, encounter_id, code, display, clinical_status, onset_ts, abatement_ts, ingest_date                                                                                                                     |
| `organization` | organization_id, name, type, city, state, postal_code, ingest_date                                                                                                                                                              |
| `practitioner` | practitioner_id, npi, full_name, gender, ingest_date                                                                                                                                                                            |

Rules: timestamps cast to `timestamp` (stored as UTC instants), IDs as plain strings (no `urn:uuid:` prefix), deduplicate within the batch. `encounter.practitioner_npi` holds the doctor's **NPI** (encounters reference doctors by NPI, not by the Practitioner's own id); it joins to `practitioner.npi`. `organization` and `practitioner` are written only for batches that contain the hospital / practitioner files (batch 1). Built by the Glue job (`docs/phase_05_glue_bronze_to_silver/README.md`).

### 6.2 Gold tables (`pf_gold`, **Apache Iceberg**, created via Athena DDL)

| Table              | Grain / key     | Notes                                                                                                                                                                                                                                         |
| ------------------ | --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dim_patient`      | patient_id      | SCD Type 1 via `MERGE`; include `age_years` (as of the day the MERGE runs), `age_group`, `is_deceased`                                                                                                                                                               |
| `dim_facility`     | organization_id | from organization                                                                                                                                                                                                                             |
| `dim_practitioner` | npi             | from practitioner; keyed on the NPI because encounters reference doctors by NPI (`practitioner_id` kept as an attribute)                                                                                                                                       |
| `dim_date`         | date            | one-time CTAS using `sequence()` + `UNNEST` (**1900-01-01 → 2030-12-31**, because the data goes back to 1924): year, quarter, month, month_name, day_of_month, day_of_week, day_name, is_weekend                                                                              |
| `fact_encounter`   | encounter_id    | patient_id, organization_id, practitioner_npi, encounter_class, start_ts, end_ts, start_date, end_date, los_hours, los_days, is_inpatient, is_emergency, reason_code, reason_display, primary_condition_code; partitioned by **`year(start_ts)`** (month gives up to 352 partitions per batch; Athena writes at most 100 per query) |

**Join to remember for gold:** `fact_encounter` takes the doctor from `encounter.practitioner_npi`; `dim_practitioner` is keyed on `npi` (the Practitioner `practitioner_id` stays as an attribute).

**MERGE rules**

- Source = silver rows for the current `ingest_date` only.
- Deduplicate the source with `ROW_NUMBER()` so each target key matches at most one row.
- `WHEN MATCHED THEN UPDATE`, `WHEN NOT MATCHED THEN INSERT`.
- Re-running the same `ingest_date` must **not** create duplicates (idempotent).
- Pass `ingest_date` from Step Functions using Athena `ExecutionParameters` or `States.Format`.

### 6.3 KPI views (`pf_gold`, Athena views)

| View                                             . | Definition                                                                                                                                                                                  |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `vw_daily_admissions_discharges`                   | inpatient admissions by `start_date`, discharges by `end_date`                                                                                                                              |
| `vw_avg_los_by_facility_month`                     | avg/median `los_days` for inpatient encounters by facility & month                                                                                                                          |
| `vw_readmission_30d`                               | inpatient encounter is a readmission if it starts within 30 days after the same patient's previous inpatient discharge (`LAG` over patient ordered by start_ts); rate by month and facility |
| `vw_ed_volume_by_hour_dow`                         | emergency encounters by hour of day × day of week                                                                                                                                           |
| `vw_top_reasons`                                   | top encounter reasons / conditions by volume                                                                                                                                                |

### Phase 4 — Ingestion Lambda (bronze)

- `lambda/ingest/handler.py`. Input: `{"batch": N}`.
  - Validate `1 <= N <= 99` (a two-digit folder `batch_NN`; there is **no `NUMBER_OF_BATCHES` setting**, a new batch needs no change); otherwise fail with a clear error.
  - Compute `ingest_date = 2026-11-01 + (N-1) days`.
  - List `landing/batch_NN/`; **fail if it is empty**.
  - Copy every object to `bronze/patient_records/ingest_date=<date>/` (server-side `copy_object`) and write `_batch_metadata.json` (batch, file count, bytes, timestamp).
  - Idempotent: running a batch again overwrites the same keys. No state file and no counter.
  - Return `{"status": "OK", "batch": N, "ingest_date": "...", "file_count": n}`. Structured logging.
- Deployed with CLI commands from a notebook: zip the code, `aws lambda create-function` / `update-function-code`.
- Test: `aws lambda invoke --function-name pf-ingest --payload ...`, then list the bronze partition.
- **Done when:** batch 1 lands in `bronze/` with a metadata file; a rerun gives the same result; batch 0 and batch 100 fail with a clear error; batch 5 works.

### Phase 5 — Glue job (bronze → silver)

- Develop logic in `glue_jobs/fhir_utils.py` (pure functions, unit tests in `tests/`).
- Dev option A (free): official AWS Glue Docker image locally against sample files. Dev option B: Glue interactive session with idle timeout ≤ 15 min (costs per minute — stop when done).
- `bronze_to_silver.py` (job argument `--ingest_date`):
  - Read `bronze/patient_records/ingest_date=<date>/*.json` with `multiLine=true` (skip `_batch_metadata.json`).
  - `explode(entry)` → filter by `resource.resourceType` → select needed fields → resolve references → cast types → dedupe.
  - Use explicit schemas if inference is slow or inconsistent.
  - **Idempotent write:** purge the target partition path first (`glueContext.purge_s3_path`), then write Parquet partitioned by `ingest_date` and **register/update tables + partitions in `pf_silver`** (e.g. `getSink(..., enableUpdateCatalog=True, partitionKeys=["ingest_date"])`). Alternative: Spark dynamic partition overwrite + Athena `ALTER TABLE ADD IF NOT EXISTS PARTITION`.
  - Log row counts per table.
- Deploy from a notebook: upload the scripts to `s3://<LAKE_BUCKET>/glue_scripts/`, then `aws glue create-job` / `update-job` (G.1X, 2 workers, timeout 10, retries 0, `--extra-py-files` for `fhir_utils.py`).
- Test: `aws glue start-job-run --job-name pf-bronze-to-silver --arguments '--ingest_date=2026-11-01'`, poll `get-job-run`, then query silver tables in Athena.
- Optional learning task: Glue Crawler over `bronze/` into `pf_bronze` to see how crawlers infer nested FHIR schemas (not part of the daily pipeline).
- **Done when:** all 5 silver tables queryable in Athena for batch 1; rerun gives the same row counts.

### Phase 6 — Gold layer (Athena + Iceberg)

- `sql/gold/ddl/`: `CREATE TABLE ... LOCATION 's3://<LAKE_BUCKET>/gold/<table>/' TBLPROPERTIES ('table_type'='ICEBERG')` for all gold tables; `dim_date` via CTAS.
- `sql/gold/merge/`: one `MERGE INTO` per table (Section 6.2 rules). Order: dims → fact.
- `sql/gold/views/`: KPI views (Section 6.3).
- Small Python helper (`infra/run_athena_sql.py`, boto3) to run a SQL file against `pf-wg` and wait for completion — used for DDL and manual testing.
- **Done when:** gold tables populated for batch 1; re-running the merges produces no duplicates; all views return sensible results.

### Phase 7 — Orchestration (Step Functions, started by hand)

- `step_functions/pf_batch_pipeline.asl.json` (template; the deploy notebook fills in ARNs, bucket and workgroup):
  1. `Ingest` - Lambda invoke (`arn:aws:states:::lambda:invoke`) with the batch number from the execution input
  2. `BronzeToSilver` - `arn:aws:states:::glue:startJobRun.sync` with `--ingest_date`
  3. `MergeDims` - sequential Athena tasks `arn:aws:states:::athena:startQueryExecution.sync`
  4. `MergeFact` - Athena task
  5. `DataQuality` - Athena DQ queries; Choice -> `Fail` if any check fails
  6. Retry (with backoff) on transient errors; `Catch` -> `Fail` state with error info
- CloudWatch logging for the state machine (level ERROR).
- Start a run: `aws stepfunctions start-execution --state-machine-arn ... --input '{"batch": 1}'`; follow it with `describe-execution` or in the Step Functions console.
